# Трапезная МДА — Backend API: дизайн

**Дата:** 2026-10-03
**Статус:** черновик на ревью
**Область:** только Backend (FastAPI). Frontend (React) — отдельный подпроект, спека позже.

---

## 1. Обзор и цель

Backend-сервис «Трапезная МДА»: HTTP API поверх PostgreSQL, обслуживающий учёт питания.

- **Питающиеся** отмечают, на какие приёмы пищи они идут, и выбирают тип питания на день.
- **Администраторы** видят питающихся своих залов и правят их отметки; в особых случаях — после дедлайна, с пометкой «Из резерва».
- **Бухгалтер** получает сводный отчёт по залам (число порций по типам + резерв) для закупки.
- **Оператор** — главный администратор: управляет аккаунтами, ролями, залами, типами питания, правилами расписания и настройками.

Ключевые технические требования:
- Синхронизация без параллельного ввода в одну **заявку** (оптимистичная блокировка).
- Предсказуемый **дедлайн** правок ради точных данных для бухгалтерии.
- Разграничение доступа по 4 ролям.

---

## 2. Роли и доступ

| Роль | Что видит | Что может |
|---|---|---|
| `eater` (питающийся) | свой календарь, свои заявки, свои дефолты | создавать/менять свои заявки до дедлайна; менять свои дефолты |
| `admin` | питающихся **своих залов** (залов может быть несколько; назначает оператор) | правки отметок и дефолтов своих питающихся; правки после дедлайна — с пометкой «Из резерва» |
| `accountant` | сводные отчёты по всем залам | только чтение отчётов |
| `operator` | всех и всё | CRUD аккаунтов, залов, типов питания, правил; настройки; логи; перегенерация дней |

Ограничения:
- **Один аккаунт = одна роль.**
- Аккаунты создаёт/удаляет и назначает пароли **только оператор**. Самостоятельной смены пароля нет.
- Питающийся привязан **ровно к одному залу**; админ — к одному и более; бухгалтер и оператор залов не имеют.
- Питающиеся **не видят** отчёты. Админы **не видят** отчёты.

## 3. Архитектура и стек

- **FastAPI** (Python 3.12), слоистая монолитная архитектура, версия API `/api/v1`.
- **Pydantic v2** — схемы; **pydantic-settings** — конфиг из `.env`.
- **SQLAlchemy 2.0 (async) + asyncpg**, миграции **Alembic**.
- **PostgreSQL 16**.
- **Аутентификация**: серверные сессии со случайным токеном (хранится хеш), привязка к отпечатку устройства, скользящий TTL 7 дней, мгновенное аннулирование при смене отпечатка.
- **Пароли**: argon2.
- **Конкурентность**: оптимистичная блокировка — версия на уровне заявки.
- **Фон**: APScheduler внутри процесса (генерация дней, очистка логов).
- **Часовой пояс**: серверное локальное время (по умолчанию `Europe/Moscow`), все вычисления и хранение — в этом поясе; фронт не конвертирует.

**Слои:**
- `api` — роутеры, только HTTP и валидация.
- `services` — бизнес-логика (дедлайн, резерв, генерация, права).
- `repositories` — запросы к БД.
- `models` / `schemas` — SQLAlchemy-модели и Pydantic-схемы.

## 4. Модель данных

### Перечисления
- `user_role`: `eater`, `admin`, `accountant`, `operator`
- `meal_kind`: `breakfast`, `lunch`, `snack` (полдник), `dinner`
- `rule_kind`: `recurring`, `one_off`

### Настройки
**`app_settings`** — одна строка (id = 1)
- `id`
- `generation_days` (N) — на сколько дней вперёд генерировать календарь
- `deadline_offset_days` (K) — за сколько дней закрывается правка
- `deadline_time` (H) — время закрытия в этот день
- `updated_at`

Значения по умолчанию при сиде: `N=14`, `K=2`, `H=13:00`.

### Справочники
**`meal_types`** — типы питания (Мясо/Пост/Рыба/…)
- `id, name (unique), sort_order, is_active, created_at, updated_at`
- Инвариант: нельзя оставить ноль активных типов (проверка в сервисе).

**`halls`** — залы
- `id, name (unique), is_active, created_at, updated_at`

### Пользователи
**`users`**
- `id, login (unique, citext), password_hash, full_name, role, default_meal_type_id (FK meal_types, null), is_active, created_at, updated_at`

**`user_meal_defaults`** — авто-значения «иду/не иду» по приёмам
- `user_id, meal_kind, is_going` — PK `(user_id, meal_kind)`

**`user_halls`** — привязка к залам
- `user_id, hall_id` — PK `(user_id, hall_id)`

### Календарь дней
**`days`** — каркас календаря
- `id, date (unique), created_at, updated_at`

**`day_hall_meals`** — снимок доступности приёмов по залам, материализованный из правил на момент генерации
- `day_id, hall_id, meal_kind, is_served` — PK `(day_id, hall_id, meal_kind)`

### Правила расписания (отдельно от календаря, чтобы не смешивать)

**`schedule_rules`** — правило исключений (создаёт оператор)
- `id, kind (recurring|one_off), is_active, created_at, updated_at`

**`schedule_rule_weekdays`** — дни недели для `recurring`-правила (отдельная таблица)
- `rule_id (FK), weekday (0–6)` — PK `(rule_id, weekday)`

**`schedule_rule_dates`** — конкретные даты для `one_off`-правила (отдельная таблица)
- `rule_id (FK), specific_date (date)` — PK `(rule_id, specific_date)`

**`schedule_rule_meals`** — какие приёмы выключаются
- `rule_id (FK), meal_kind` — PK

**`schedule_rule_halls`** — на какие залы действует
- `rule_id (FK), hall_id` — PK

Семантика правил: правило **выключает** перечисленные приёмы для назначенных залов. База — «все 4 приёма идут».
- `recurring` — выключение действует в указанные дни недели (строки в `schedule_rule_weekdays`, их может быть несколько).
- `one_off` — выключение действует на указанные даты (строки в `schedule_rule_dates`).
Правила только выключают, конфликтов «вкл/выкл» нет.

### Заявки
**`requests`** — заявка питающегося на день
- `id, user_id (FK), date, meal_type_id (FK), version, created_at, updated_at`
- unique `(user_id, date)`

**`request_items`** — отметки по приёмам внутри заявки
- `id, request_id (FK), meal_kind, is_going, is_reserve`
- unique `(request_id, meal_kind)`

Заявка создаётся **лениво** при первой правке дня и **никогда не удаляется**. Если заявки нет — действуют дефолты пользователя.

### Служебное
**`sessions`**
- `id, user_id (FK), token_hash (unique), device_fingerprint_hash, created_at, last_seen_at, expires_at, revoked_at (null)`

**`audit_logs`** — короткоживущие логи действий
- `id, user_id (null), action, entity_type, entity_id, details (jsonb), created_at`
- Пишутся из слоя сервисов на все мутации. Хранятся ~2 суток, чистятся ежедневно (см. §12).

## 5. Аутентификация и сессии

**Вход** `POST /api/v1/auth/login`
- Тело: `{login, password}`. Заголовок `X-Device-Fingerprint: <hash>` (отпечаток вычисляет клиент).
- Проверяем `login` + `password` (argon2), статус `is_active`.
- Генерируем **случайный токен** (32 байта, `secrets.token_urlsafe`), сохраняем в `sessions` **хеш** токена (SHA-256), `device_fingerprint_hash` (SHA-256 от отпечатка), `expires_at = now + 7 дней`.
- Возвращаем сырой токен клиенту (хранится только на клиенте).

**Отпечаток устройства** (B3): клиент при первом входе генерирует случайный UUID и хранит в `localStorage`; отпечаток = `sha256(device_uuid + ":" + user_agent)`. Отправляется заголовком на каждом запросе.

**Каждый защищённый запрос**
1. `Authorization: Bearer <token>` → находим сессию по хешу токена.
2. Сессия не отозвана и не истекла, иначе `401`.
3. `device_fingerprint_hash` совпадает, иначе сессия **немедленно аннулируется** (`revoked_at = now`) → `401`.
4. Обновляем `last_seen_at` и продлеваем `expires_at = now + 7 дней` (скользящий TTL).
5. Загружаем пользователя, проверяем `is_active`.

**Выход** `POST /api/v1/auth/logout` — `revoked_at = now` текущей сессии.

**Профиль** `GET /api/v1/auth/me` — `{id, login, full_name, role, halls:[...], default_meal_type_id}`.

Пароли: хранятся локально, смена — только оператором (`PUT /operator/users/{id}/password`, сброс). Эндпоинта смены пароля самим пользователем **нет**.

## 6. Расписание, дедлайн, резерв

### Дедлайн
День `D` закрывается в момент `deadline(D) = (D − K) в H:00` (K и H из `app_settings`, локальное время).
- `now < deadline(D)` — питающийся и админ правят **без пометки**.
- `now >= deadline(D)` — питающийся получает `403`; админ правит **с пометкой `is_reserve = true`**.
- Дедлайн общий для всех залов и всех дней; переопределения на конкретный день нет.

**Разбор на примере** `сегодня = 03.10`, `K = 3`, `H = 13:00`. Формула: закрытие дня `D` — это `(D − 3 дня) в 13:00`.

| День `D` | Дедлайн `deadline(D)` | Правка в 03.10 **10:00** | Правка в 03.10 **14:00** |
|---|---|---|---|
| 03.10 (сегодня) | 30.09 13:00 | закрыто | закрыто |
| 04.10 (+1) | 01.10 13:00 | закрыто | закрыто |
| 05.10 (+2) | 02.10 13:00 | закрыто | закрыто |
| 06.10 (+3) | **03.10 13:00** | открыто | закрыто |
| 07.10 (+4) | 04.10 13:00 | открыто | открыто |

Итог: до 13:00 дня `03.10` доступен ещё `06.10` (ровно граница `D = today + K`), после 13:00 он закрывается — то есть фактически недоступны `03.10…06.10`. Значение `K` — настройка, поэтому граница регулируется (например, при `K = 2` последний открытый день — `05.10`).

### Резерв
- `request_items.is_reserve` — «порция из резерва».
- Правило: админская правка после дедлайна помечает затронутые «иду»-порции `is_reserve = true`.
- Если админ после дедлайна меняет **тип питания дня** — помечаются **все** «иду»-порции этого дня.
- Если админ выключает приём (`is_going = false`) — у этой позиции `is_reserve` сбрасывается.

### Эффективные значения дня
Для пары (пользователь, дата):
- Если есть `request` — берём `requests.meal_type_id` и `request_items` по приёмам.
- Если `request` нет — берём дефолты: `users.default_meal_type_id` и `user_meal_defaults`.
- Учитываются только приёмы, где `day_hall_meals.is_served = true` для зала пользователя.

## 7. Генерация календаря

Задача APScheduler ежедневно в **23:59** (см. §12):
1. Для дат `[today+1 .. today+N]`, которых нет в `days`, создаём строки `days`.
2. Для каждой такой даты и каждого зала вычисляем доступность приёмов: базово все 4 `is_served = true`, затем применяем активные правила:
   - `recurring`: если `weekday(date)` есть в `schedule_rule_weekdays` правила;
   - `one_off`: если `date` есть в `schedule_rule_dates` правила;
   - и `hall` входит в `schedule_rule_halls`;
   → для приёмов из `schedule_rule_meals` ставим `is_served = false`.
3. Записываем в `day_hall_meals`.

**Перегенерация (перезапись календаря):**
- Идемпотентна: повторный запуск не дублирует строки, а **пересчитывает** `day_hall_meals` для дат горизонта по текущим правилам (upsert).
- Диапазон перегенерации — `[today .. today+N]` (прошедшие дни, `< today`, не трогаем).
- **Возврат приёма**: если правило, выключавшее приём, удалено или деактивировано, после перегенерации приём снова становится `is_served = true`. Заявки питающихся при этом сохраняются — если приём снова включён, уже сделанные заявки по нему продолжают учитываться.
- **Автозапуск**: перегенерация выполняется автоматически при создании/изменении/удалении правила и при изменении `N`.
- **Кнопка оператора**: `POST /operator/days/regenerate` с телом `{from, to}` (в пределах горизонта) — «переписать» вручную.
- При старте приложения задача **догоняет** пропущенное (если сервер был выключен).

## 8. Заявки: создание и правка

**Создание (ленивое).** При первой правке дня сервис в одной транзакции:
1. Создаёт `requests` c `meal_type_id = default_meal_type_id` пользователя и `version = 1`.
2. Создаёт `request_items` по **всем** приёмам (`is_going` из `user_meal_defaults`, иначе `false`; `is_reserve = false`).
3. Применяет присланную правку.
4. Пишет запись в `audit_logs`.

Гонка на создании защищена unique `(user_id, date)`: проигравший получает `409`.

**Правка существующей заявки** — по версии (см. §9).

**Кто правит.** И питающийся, и админ используют одну и ту же сущность. Разница — только в правах и в пометке резерва после дедлайна.

## 9. Конкурентный доступ

Оптимистичная блокировка, **версия на уровне заявки** (`requests.version`).

- Клиент присылает `version`, которую прочитал.
- Обновление выполняется как `UPDATE ... WHERE id = ? AND version = ?` c `version = version + 1`.
- Если обновлено 0 строк → `409 Conflict`, тело: `{detail: "record_changed", current: <актуальное состояние дня>}`.
- Клиент показывает предупреждение «данные изменились, обновите» и не перезаписывает чужую правку автоматически.
- Создание заявки (`version` не прислан) при уже существующей → `409`.

Одна версия на день: параллельная правка разных приёмов одного дня тоже конфликтует. Это принято сознательно (день — единица редактирования).

## 10. HTTP API (v1)

Все защищённые запросы: `Authorization: Bearer <token>` + `X-Device-Fingerprint`.

### 10.1 Аутентификация
- `POST /api/v1/auth/login`
- `POST /api/v1/auth/logout`
- `GET  /api/v1/auth/me`

### 10.2 Питающийся (и любой вошедший для личных данных)
- `GET  /api/v1/me/defaults` → `{default_meal_type_id, meals:{breakfast,lunch,snack,dinner}}`
- `PUT  /api/v1/me/defaults` — тело: `{default_meal_type_id, meals:{...}}`
- `GET  /api/v1/me/calendar?from=&to=` → список дней: `{date, meals:[{meal_kind,is_served}], meal_type_id, items:[{meal_kind,is_going,is_reserve}], version, deadline_at, editable}`
- `PUT  /api/v1/me/days/{date}` — тело: `{meal_type_id, meals:{breakfast,lunch,snack,dinner}, version?}`
  - до дедлайна: создаёт/обновляет заявку, `200`/`201`;
  - после дедлайна: `403`;
  - конфликт версий: `409`.

### 10.3 Админ (в рамках своих залов)
- `GET  /api/v1/admin/users?hall_id=` — питающиеся зала (+ дефолты, тип)
- `GET  /api/v1/admin/requests?date=&hall_id=` — питающиеся на дату: эффективные значения и признак наличия заявки
- `PUT  /api/v1/admin/requests/{user_id}/{date}` — тело как в 10.2; после дедлайна ставит `is_reserve`
- `PUT  /api/v1/admin/users/{user_id}/defaults` — правка дефолтов своего питающегося

### 10.4 Бухгалтер
- `GET  /api/v1/accountant/report?date=&hall_id=` — свод на дату, см. §11
- `GET  /api/v1/accountant/report/period?from=&to=&hall_id=` — суммы за период (без персональных данных), см. §11

### 10.5 Оператор
- `GET/POST/PUT/DELETE /api/v1/operator/users` (+ `PUT /operator/users/{id}/password`, `PUT /operator/users/{id}/halls`)
  - удаление: по умолчанию **мягкое** (`is_active=false`); **жёсткое удаление** — отдельным флагом `hard=true`
- `GET/POST/PUT/DELETE /api/v1/operator/halls`
- `GET/POST/PUT/DELETE /api/v1/operator/meal-types`
- `GET/POST/PUT/DELETE /api/v1/operator/schedule-rules`
- `GET/PUT /api/v1/operator/settings` — `{generation_days, deadline_offset_days, deadline_time}`
- `POST /api/v1/operator/days/regenerate` — `{from, to}`
- `GET /api/v1/operator/logs?from=&to=&user_id=` — логи за последние ~2 суток

Доступ — зависимость `require_roles(...)`. Админ дополнительно ограничен своими залами (проверка в сервисе → `403` при чужом зале).

## 11. Отчёт бухгалтера

`GET /api/v1/accountant/report?date=YYYY-MM-DD&hall_id=<optional>`

На дату (для каждого зала, при желании — по одному залу):
- по каждому приёму (`breakfast`, `lunch`, `snack`, `dinner`):
  - блок **типов**: число порций по каждому типу питания (`count` «иду»);
  - блок **резерва по типам**: число «иду» с `is_reserve = true`, по каждому типу;
  - `total` и `reserve_total` по приёму;
- **итог за день** по залу и **итог по резервам**.

Форма ответа:
```json
{
  "date": "2026-10-03",
  "halls": [
    {
      "hall_id": 1,
      "hall_name": "Зал №1",
      "meals": [
        {
          "meal_kind": "breakfast",
          "by_type": [
            {"meal_type_id": 1, "name": "Мясо", "count": 30},
            {"meal_type_id": 2, "name": "Пост", "count": 5},
            {"meal_type_id": 3, "name": "Рыба", "count": 10}
          ],
          "reserve_by_type": [
            {"meal_type_id": 1, "name": "Мясо", "count": 2},
            {"meal_type_id": 2, "name": "Пост", "count": 0},
            {"meal_type_id": 3, "name": "Рыба", "count": 1}
          ],
          "total": 45,
          "reserve_total": 3
        }
      ],
      "day_total": 180,
      "day_reserve_total": 8
    }
  ],
  "grand_total": 180,
  "grand_reserve_total": 8
}
```

Подсчёт: по каждому питающемуся зала берём эффективные значения дня (§6); учитываем только `is_served = true` приёмы; суммируем по типу питания и отдельно по `is_reserve`. Числа порций — только для «иду».

### Отчёт за период (только суммы, без персональных данных)

`GET /api/v1/accountant/report/period?from=YYYY-MM-DD&to=YYYY-MM-DD&hall_id=<optional>`

Возвращает суммы за диапазон дат: по каждому залу и приёму — итоги по типам питания и по резерву. **Без фамилий и без разбивки по людям** — только агрегированные числа.

```json
{
  "from": "2026-10-01",
  "to": "2026-10-07",
  "halls": [
    {
      "hall_id": 1,
      "hall_name": "Зал №1",
      "meals": [
        {
          "meal_kind": "breakfast",
          "by_type": [
            {"meal_type_id": 1, "name": "Мясо", "count": 210},
            {"meal_type_id": 2, "name": "Пост", "count": 35},
            {"meal_type_id": 3, "name": "Рыба", "count": 70}
```

## 12. Фоновые задачи (APScheduler)

Ежедневно в 23:59 (локальное время), а также один раз при старте приложения («догон»):

1. **Генерация календаря** — см. §7.
2. **Очистка логов** — `DELETE FROM audit_logs WHERE created_at < (сегодня 00:00)`.
   То есть лог, созданный в день `D`, живёт весь `D` и весь `D+1` и удаляется в 23:59 `D+1`.

Помимо ежедневного запуска, перегенерация горизонта запускается автоматически при изменении правил и `N` (см. §7).

## 13. Проверки и права (сводно)

- `eater`: только свои заявки/дефолты; после дедлайна — запрет.
- `admin`: только питающиеся своих залов; после дедлайна — правки с `is_reserve`.
- `accountant`: только отчёты.
- `operator`: всё, кроме правки заявок питающихся (оператор в отметках не участвует).
- Создание/удаление аккаунтов и пароли — только оператор.
- Инварианты: не менее одного активного `meal_type`; у `eater` ровно один зал; у `admin` ≥ 1 зал.

## 15. Тестирование

`pytest` + `pytest-asyncio` + `httpx.AsyncClient`; отдельная тестовая БД PostgreSQL.

Покрываем (обязательный минимум):
- логин/логаут; `401` при истёкшей/отозванной сессии; мгновенный сброс при смене отпечатка.
- дедлайн: правка до дедлайна (без пометки) и после (питающийся `403`, админ с `is_reserve`).
- резерв: смена типа админом после дедлайна помечает все «иду»-порции; выключение приёма сбрасывает флаг.
- конкурентность: второй писатель получает `409` и актуальное состояние.
- ленивое создание заявки; гонка на unique `(user_id, date)`.
- генерация: материализация правил (recurring по дню недели, one_off по дате, привязка к залам), идемпотентность.
- отчёт: подсчёт по типам и резерву, учёт только `is_served`, применение дефолтов при отсутствии заявки.
- права: админ не видит чужие залы; питающийся не видит отчёты.

## 18. Глоссарий

- **Заявка (`request`)** — явный выбор питающегося на конкретную дату (тип питания + «иду/не иду» по приёмам), создаётся лениво и не удаляется.
- **Дефолты** — автоматические значения пользователя (`user_meal_defaults`, `users.default_meal_type_id`), действуют, пока нет заявки.
- **Дедлайн** — момент `(D − K)` в `H:00`, после которого питающийся править не может.
- **Резерв (`is_reserve`)** — пометка порции, изменённой админом после дедлайна.
- **Правило (`schedule_rule`)** — выключение приёмов для выбранных залов (по дню недели или на дату).
- **Снимок дня (`day_hall_meals`)** — материализованная доступность приёмов по залам на дату.
