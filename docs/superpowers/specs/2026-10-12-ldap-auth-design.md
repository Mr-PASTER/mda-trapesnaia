# Трапезная МДА — аутентификация через LDAP: дизайн

Дата: 2026-10-12. Статус: на согласовании.

## 1. Цель

Добавить вход через LDAP для питающихся, не меняя существующую локальную
аутентификацию служебных ролей и не затрагивая данные, которые уже ведутся
в Postgres.

Две базы, два разных владельца данных:

| | LDAP (только чтение) | PostgreSQL (владеем мы) |
|---|---|---|
| Логин | источник истины | хранится для отображения |
| Пароль | источник истины, у нас **не хранится** | заглушки нет (`NULL`) |
| ФИО | источник истины | кэш, обновляется при входе и синком |
| Роль, залы | — | назначает оператор |
| Тип питания, приёмы, заявки, сессии | — | всё наше |

Ключевое ограничение: **пароль проверяется живым `bind` в момент входа**.
Синхронизировать пароли нельзя — их не прочитать, а локальная копия устареет
при первой же смене пароля в каталоге. Поэтому «ежедневная подгрузка» относится
только к справочным данным, не к учётным.

## 2. Границы

Входит: вход через LDAP для питающихся, ленивое создание локальной записи при
первом входе, ночной синк справочных данных, конфигурация через `.env`.

Не входит: назначение ролей и залов из групп каталога, массовый импорт всех
учёток под `BASE_DN`, переключатель `auth_source` в UI, смена пароля LDAP из
приложения, SASL/Kerberos.

## 3. Правила, зафиксированные с заказчиком

1. LDAP — только для `eater`. `operator`, `admin`, `accountant` остаются
   локальными (argon2 в Postgres).
2. Переключателя `ldap` ↔ `local` нет ни в UI, ни в CLI.
3. Все пользователи, существующие в Postgres на момент миграции, остаются
   `auth_source = local` и **LDAP их не трогает**: ни вход, ни синк.
4. `auth_source = ldap` получают только записи, созданные при входе через LDAP.
5. Локальные пользователи никогда не удаляются — только `is_active = false`.
6. LDAP недоступен → вход LDAP-пользователей не проходит (локальный оператор
   входит как обычно).

## 4. Конфигурация (`.env`)

Обязательные (значения даёт заказчик):

| Переменная | Пример | Назначение |
|---|---|---|
| `LDAP_HOST` | `dc.example.org:389` | хост, допускается схема и порт |
| `LDAP_VERSION` | `3` | версия протокола |
| `LDAP_BASE_DN` | `ou=people,dc=example,dc=org` | база поиска |
| `LDAP_BIND_DN` | `cn=svc,ou=service,dc=…` | сервисная учётка |
| `LDAP_BIND_PASSWORD` | — | её пароль |

Необязательные (безопасные дефолты):

| Переменная | Дефолт | Назначение |
|---|---|---|
| `LDAP_ENABLED` | `false` | главный выключатель; `false` — поведение как сейчас |
| `LDAP_TLS` | `none` | `none` \| `starttls` \| `ldaps` |
| `LDAP_TLS_VERIFY` | `true` | проверять сертификат |
| `LDAP_TLS_CA_CERT` | — | путь к CA при самоподписанном сертификате |
| `LDAP_LOGIN_FILTER` | `(\|(uid={login})(sAMAccountName={login}))` | поиск по логину, `{login}` подставляется экранированным |
| `LDAP_NAME_ATTR` | `cn` | ФИО (в AD обычно `displayName`) |
| `LDAP_ID_ATTR` | `entryUUID` | стабильный ID (в AD `objectGUID`) |
| `LDAP_USER_FILTER` | — | доп. условие, напр. `(memberOf=cn=trapeznaya,…)` |
| `LDAP_TIMEOUT` | `5` | таймаут соединения и ответа, сек |
| `LDAP_SYNC_ENABLED` | `false` | ночной синк |
| `LDAP_SYNC_HOUR` | `3` | час запуска синка |

`LDAP_ENABLED=false` — единственный способ полностью вернуть прежнее поведение
без отката миграции.

## 5. Модель данных

Миграция Alembic добавляет в `users`:

- `auth_source` — enum `local | ldap`, `NOT NULL`, `server_default='local'`;
- `ldap_uid` — `String(128)`, nullable, **уникальный частичный индекс**
  (там, где не `NULL`): стабильный идентификатор из каталога;
- `ldap_dn` — `String(512)`, nullable: DN на момент последнего входа
  (диагностика и fallback-сопоставление);
- `password_hash` — становится **nullable** (у LDAP-пользователей пароля нет).

Существующие строки получают `auth_source='local'`; `password_hash` не
изменяется. Откат миграции безопасен: столбцы nullable, удаление не ломает
данные.

## 6. Поток входа

`POST /api/v1/auth/login` (схема, cookie и отпечаток устройства не меняются):

```
user = users.get_by_login(login)
if user and user.auth_source == "local":
    return user if user.is_active and verify_password(user.password_hash, password) else None
if not settings.ldap_enabled:
    return None
identity = ldap.authenticate(login, password)     # может бросить LdapUnavailable
if identity is None:
    return None
return await upsert_ldap_user(db, identity)
```

`ldap.authenticate`:

1. Отклонить пустой/пробельный пароль до обращения к серверу (иначе возможен
   «неаутентифицированный bind»).
2. Подключиться (с учётом `LDAP_TLS`) и `bind` сервисной учёткой.
3. Поиск под `LDAP_BASE_DN` фильтром
   `(&<LDAP_LOGIN_FILTER с экранированным логином><LDAP_USER_FILTER>)`,
   запрашивая `dn`, `LDAP_NAME_ATTR`, `LDAP_ID_ATTR`.
4. Ровно одна запись → отсоединиться и выполнить **новый `bind`** найденным DN
   с введённым паролем.
5. Успех → `LdapIdentity(uid, dn, login, full_name)`; неверный пароль → `None`.

Все вызовы `ldap3` — блокирующие, поэтому выполняются в `asyncio.to_thread`
(один поток на вход, без пула соединений: bind → search → rebind дешевле держать
короткоживущими).

## 7. Upsert локальной записи

Порядок поиска и правила:

1. По `ldap_uid = identity.uid` → найдено: обновить `full_name` и `ldap_dn`,
   остальное не трогать. Если `is_active = false` → вход запрещён (`401`).
2. Иначе по `login` (в нижнем регистре):
   - найдено и `auth_source = local` → **вход запрещён** (`401`): локальную
     учётку LDAP не перехватывает. Конфликт разрешается вручную — переименовать
     логин в каталоге либо в БД; автоматического переключения нет;
   - найдено и `auth_source = ldap` → связать: проставить `ldap_uid`,
     `ldap_dn`, обновить `full_name`;
3. Иначе создать: `login`, `full_name` из каталога, `role = eater`,
   `auth_source = ldap`, `password_hash = NULL`, `is_active = true`.

Роль, залы, `default_meal_type_id` и все прикладные данные при upsert
**не изменяются**.

Новый питающийся получает запись без залов: он сможет войти, но меню будет
пустым, пока оператор не назначит зал.

## 8. Ошибки

| Ситуация | Ответ |
|---|---|
| Неверный пароль, логин отсутствует, найдено > 1 записи | `401 invalid_credentials` |
| Пустой пароль | `401 invalid_credentials` (без обращения к LDAP) |
| Локальная учётка с таким логином существует | `401 invalid_credentials` |
| Локальная запись отключена оператором | `401 invalid_credentials` |
| Каталог недоступен / таймаут / ошибка TLS | `503 ldap_unavailable` |
| `LDAP_ENABLED=false` и пользователь не локальный | `401 invalid_credentials` |

`503` отделён от `401` намеренно: на экране входа это разные сообщения —
«Каталог недоступен, попробуйте позже» против «Неверный логин или пароль».
Фронтенд получает новую ветку обработки в `LoginPage`.

## 9. Ночной синк

Задача в существующем `AsyncIOScheduler`, включается `LDAP_SYNC_ENABLED=true`.

1. Выбрать всех `auth_source = 'ldap'` (пачками по 100).
2. Найти их в каталоге по `ldap_uid` (фильтр
   `(|(<LDAP_ID_ATTR>=a)(<LDAP_ID_ATTR>=b)…)`), запрашивая DN и ФИО.
3. Найден → обновить `full_name` и `ldap_dn`.
4. Не найден → `is_active = false` (не удалять: заявки и отчётность).
5. Новых не создаёт; пользователей с `auth_source = local` не читает и не
   меняет.

Каталог недоступен → предупреждение в лог, изменения не применяются, повтор
на следующую ночь (без очереди «долгов»).

## 10. Безопасность

- Экранирование логина по RFC 4515 (`\ * ( ) NUL`) перед подстановкой в фильтр.
- Пароли (сервисный и пользовательский) не логируются и не сохраняются.
- `LDAP_TLS=none` допустим только во внутренней сети; в README — предупреждение
  и рекомендация `starttls`/`ldaps`.
- Таймаут на соединение и ответ, чтобы недоступный каталог не подвешивал вход.
- Сервисная учётка используется только для поиска; записи в каталог не
  выполняются никогда.

## 11. Тестирование

LDAP-клиент выделяется в интерфейс и подменяется в тестах фейком — реальный
сервер для CI не нужен.

Вход:
- первый вход LDAP-пользователя создаёт `eater` с `auth_source=ldap`;
- повторный вход не дублирует запись и обновляет ФИО;
- неверный пароль → `401`, счётчик попыток не создаёт записи;
- пустой пароль не доходит до клиента;
- локальный оператор входит по паролю, LDAP не вызывается;
- локальный `eater` не перехватывается LDAP (`401`);
- отключённая запись → `401`;
- каталог недоступен → `503`;
- экранирование: логин `*)(uid=*` не расширяет фильтр (проверяется на уровне
  сформированного фильтра).

Синк:
- переименование обновляет ФИО;
- отсутствующий в каталоге становится `is_active=false`;
- локальные пользователи не меняются;
- недоступный каталог не меняет ничего.

Конфигурация:
- `LDAP_ENABLED=false` — прежнее поведение целиком.

## 12. Выкат и откат

1. Миграция добавляет столбцы; все существующие записи — `local`.
2. Заполнить `LDAP_*` в `.env`, оставить `LDAP_ENABLED=false` — поведение не
   меняется, приложение поднимается как раньше.
3. Включить `LDAP_ENABLED=true`, проверить вход одним тестовым питающимся.
4. Назначить зал, проверить меню.
5. Включить `LDAP_SYNC_ENABLED=true`.

Откат: `LDAP_ENABLED=false` (мгновенно, без пересборки БД). Откат миграции
необязателен и безопасен.

## 13. Зависимости

`ldap3` (чистый Python, без сборки C-расширений в `python:3.12-slim`).

## 14. Известные ограничения

- Питающийся, которого нет в каталоге, войти не сможет — переключателя нет по
  решению заказчика.
- Совпадение логина локальной учётки и LDAP-пользователя трактуется в пользу
  локальной: LDAP такой вход отклоняет.
- Логины приводятся к нижнему регистру (как в существующем `create_operator`);
  в каталоге различающиеся только регистром логины не поддерживаются.
