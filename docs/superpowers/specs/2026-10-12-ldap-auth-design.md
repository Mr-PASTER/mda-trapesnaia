# Трапезная МДА — аутентификация через LDAP: дизайн

Дата: 2026-10-12 (обновлено). Статус: на согласовании.

## 1. Цель

Добавить вход через LDAP для питающихся, не меняя существующую локальную
аутентификацию, и держать в Postgres полный список людей из каталога, чтобы
администратор и оператор видели их в приложении, а бухгалтерия их учитывала.

Две базы, два разных владельца данных:

| | LDAP (только чтение) | PostgreSQL (владеем мы) |
|---|---|---|
| Логин | источник истины | кэш, обновляется при входе и синком |
| Пароль | источник истины, у нас **не хранится** | заглушки нет (`NULL`) |
| ФИО | источник истины | кэш, обновляется при входе и синком |
| Роль, залы | — | назначает оператор |
| Тип питания, приёмы, заявки, сессии | — | всё наше |

Ключевое ограничение: **пароль проверяется живым `bind` в момент входа**.
Синхронизировать пароли нельзя — их не прочитать, а локальная копия устареет
при первой же смене пароля в каталоге. Синк относится только к справочным
данным.

## 2. Границы

Входит: вход через LDAP, автоматическое создание локальной записи (при входе и
при синке), назначение первого зала, ежедневный синк в 23:59, раздельное
отображение «Студенты / Внешние» в интерфейсе администратора и оператора.

Не входит: назначение ролей и залов из групп каталога, переключатель
`auth_source` в UI, смена пароля LDAP из приложения, SASL/Kerberos,
дополнительные атрибуты каталога (почта, телефон) — для них нет полей.

## 3. Правила, зафиксированные с заказчиком

1. LDAP используется только для `eater`. `operator`, `admin`, `accountant`
   остаются локальными (argon2 в Postgres).
2. Переключателя `ldap` ↔ `local` нет ни в UI, ни в CLI.
3. Служебные и вручную заведённые пользователи (`auth_source = local`)
   неприкосновенны: LDAP не перехватывает их вход, синк их не читает и не
   меняет. Это второй, независимый «тип входа».
4. `auth_source = ldap` получают только записи, созданные из каталога.
5. Пользователи из каталога **импортируются в Postgres** при синке и создаются
   при первом входе — чтобы админ, оператор и отчётность их видели.
6. При создании питающегося автоматически назначается **первый активный зал по
   алфавиту** (так же сортируется список залов в интерфейсе).
7. Локальные пользователи никогда не удаляются — только `is_active = false`.
8. LDAP недоступен → вход LDAP-пользователей не проходит, локальный оператор
   входит как обычно.
9. Разделение «Студенты / Внешние» есть у администратора и оператора.
   Бухгалтер разделения не видит: в отчётах все равны.

## 4. Конфигурация (`.env`)

Обязательные (значения даёт заказчик):

| Переменная | Пример | Назначение |
|---|---|---|
| `LDAP_HOST` | `dc.example.org:389` | хост, допускается схема и порт |
| `LDAP_VERSION` | `3` | версия протокола |
| `LDAP_BASE_DN` | `ou=people,dc=example,dc=org` | база поиска |
| `LDAP_BIND_DN` | `cn=svc,ou=service,dc=…` | сервисная учётка |
| `LDAP_BIND_PASSWORD` | — | её пароль |

Необязательные (безопасные дефолты):

| Переменная | Дефолт | Назначение |
|---|---|---|
| `LDAP_ENABLED` | `false` | главный выключатель; `false` — поведение как сейчас |
| `LDAP_TLS` | `none` | `none` \| `starttls` \| `ldaps` |
| `LDAP_TLS_VERIFY` | `true` | проверять сертификат |
| `LDAP_TLS_CA_CERT` | — | путь к CA при самоподписанном сертификате |
| `LDAP_LOGIN_FILTER` | `(\|(uid={login})(sAMAccountName={login}))` | поиск при входе, `{login}` подставляется экранированным |
| `LDAP_NAME_ATTR` | `cn` | ФИО (в AD обычно `displayName`) |
| `LDAP_ID_ATTR` | `entryUUID` | стабильный ID (в AD `objectGUID`) |
| `LDAP_USER_FILTER` | — | доп. условие для входа, напр. `(memberOf=cn=mdausers,…)` |
| `LDAP_SYNC_FILTER` | — | фильтр импорта; если пуст — берётся `LDAP_USER_FILTER` |
| `LDAP_TIMEOUT` | `5` | таймаут соединения и ответа, сек |
| `LDAP_SYNC_ENABLED` | `false` | ежедневный синк |
| `LDAP_SYNC_HOUR` | `23` | час запуска; минута фиксирована — `59` |

Требования к фильтрам:

- `LDAP_SYNC_FILTER` определяет, **кто попадёт в Postgres**. Он не должен быть
  шире того, что допускается к входу: импортированный человек, который не может
  войти, — мёртвая запись в списках.
- Если синк включён, а `LDAP_SYNC_FILTER` и `LDAP_USER_FILTER` пусты, синк
  отказывается работать и пишет ошибку в лог: импортировать весь каталог по
  умолчанию недопустимо. Попытка входа при этом работает как обычно.

`LDAP_ENABLED=false` — способ полностью вернуть прежнее поведение без отката
миграции.

## 5. Интеграция модуля

Docker собирается из `server/` (`build: .`), поэтому пакет в корне репозитория
образу не виден. Выбран вариант A: модуль переносится внутрь приложения.

- `ldap_module/ldap_auth/` → `server/app/integrations/ldap/`
  (импорт `app.integrations.ldap`), включая CLI (`python -m app.integrations.ldap`).
- Тесты модуля → `server/tests/` (фейковый коннектор, реальный сервер не нужен).
- `ldap3` добавляется в зависимости `server/pyproject.toml`.
- В `LdapSettings` добавляется поле `sync_filter`; дефолт `sync_hour` меняется на
  `23` (модуль больше не самостоятельный пакет).
- Секреты (`ldap_module/.env`) остаются вне git; в контейнер `LDAP_*` попадают
  через `environment` в compose.

## 6. Модель данных

Миграция Alembic добавляет в `users`:

- `auth_source` — enum `local | ldap`, `NOT NULL`, `server_default='local'`;
- `ldap_uid` — `String(128)`, nullable, **уникальный частичный индекс**
  (там, где не `NULL`): стабильный идентификатор из каталога;
- `ldap_dn` — `String(512)`, nullable: DN на момент последнего входа/синка;
- `password_hash` — становится **nullable** (у LDAP-пользователей пароля нет).

Существующие строки получают `auth_source='local'`; `password_hash` не
изменяется. Откат миграции безопасен.

`auth_source` попадает в API через `UserOut` (а значит в `/auth/me`,
`/admin/users` и список оператора) — на нём строится разделение в интерфейсе.

## 7. Поток входа

`POST /api/v1/auth/login` (схема, cookie и отпечаток устройства не меняются):

```
user = users.get_by_login(login)
if user and user.auth_source == "local":
    return user if user.is_active and verify_password(user.password_hash, password) else None
if not settings.ldap_enabled:
    return None
identity = ldap.authenticate(login, password)     # может бросить LdapUnavailable
if identity is None:
    return None
return await upsert_ldap_user(db, identity)
```

`ldap.authenticate` (реализовано в модуле): отклонить пустой пароль → bind
сервисной учёткой → поиск по `LDAP_LOGIN_FILTER` + `LDAP_USER_FILTER` с
экранированием по RFC 4515 → ровно одна запись → новый bind найденным DN с
введённым паролем → `LdapIdentity(uid, dn, login, full_name)`.
Блокирующие вызовы выполняются в `asyncio.to_thread`.

## 8. Создание и обновление локальной записи

Общая функция `upsert_ldap_user(db, identity)` используется и при входе, и при
синке.

Порядок поиска и правила:

1. По `ldap_uid = identity.uid` → найдено: обновить `full_name` и `ldap_dn`;
   `login` обновить, если он изменился в каталоге и не занят другой записью.
   Если `is_active = false`, автоматически обратно **не включаем** (это решение
   администратора): при входе — `401`, при синке — пропустить.
2. Иначе по `login`:
   - найдено и `auth_source = local` → **не трогать**: локальную учётку LDAP не
     перехватывает. При входе — `401`, при синке — пропустить и записать
     предупреждение;
   - найдено и `auth_source = ldap` → связать: проставить `ldap_uid`,
     `ldap_dn`, обновить `full_name`.
3. Иначе создать: `login`, `full_name` из каталога, `role = eater`,
   `auth_source = ldap`, `password_hash = NULL`, `is_active = true`,
   **зал — первый активный по алфавиту**.

Роль, залы, `default_meal_type_id` и прикладные данные при обновлении
**не изменяются**; зал назначается только при создании.

Если активных залов нет, создать питающегося нельзя (модель требует ровно один
зал): при входе — `503 no_hall_available`, при синке — ошибка в лог и остановка
прогона.

## 9. Ошибки входа

| Ситуация | Ответ |
|---|---|
| Неверный пароль, логин отсутствует, найдено > 1 записи | `401 invalid_credentials` |
| Пустой пароль | `401 invalid_credentials` (без обращения к LDAP) |
| Локальная учётка с таким логином существует | `401 invalid_credentials` |
| Локальная запись отключена оператором | `401 invalid_credentials` |
| Нет активных залов для создания питающегося | `503 no_hall_available` |
| Каталог недоступен / таймаут / ошибка TLS | `503 ldap_unavailable` |
| `LDAP_ENABLED=false` и пользователь не локальный | `401 invalid_credentials` |

`503` отделён от `401` намеренно: на экране входа это разные сообщения —
«Каталог недоступен, попробуйте позже» против «Неверный логин или пароль».
Фронтенд получает новую ветку обработки в `LoginPage`.

## 10. Ежедневный синк

Отдельная задача в существующем `AsyncIOScheduler`, включается
`LDAP_SYNC_ENABLED=true`; запуск в `LDAP_SYNC_HOUR:59`, по умолчанию **23:59**.
Полная сверка:

1. Поиск в каталоге по `LDAP_SYNC_FILTER` под `LDAP_BASE_DN` (пачками, атрибуты
   `dn`, `LDAP_NAME_ATTR`, `LDAP_ID_ATTR`).
2. Для каждой найденной записи — `upsert_ldap_user` (создание с первым залом
   либо обновление ФИО/логина).
3. Все `auth_source = ldap`, которых в каталоге больше нет → `is_active = false`.
   Не удалять: заявки и отчётность должны сохраниться.
4. Пользователи с `auth_source = local` не читаются и не меняются.

Синк идемпотентен: повторный прогон не создаёт дублей. Каталог недоступен →
предупреждение в лог, изменения не применяются, повтор на следующую ночь.
Результат прогона (создано / обновлено / отключено) пишется в лог.

## 11. Отображение: студенты и внешние

- **Администратор** (`PeoplePage`): два раздела — «Студенты» (`auth_source =
  ldap`) и «Внешние» (`local`), со счётчиками; поиск работает внутри активного
  раздела. Данные о залах, переход в меню и настройки человека — как сейчас.
- **Оператор** (`/operator/users`): в таблице бейдж «LDAP» / «локальный»;
  фильтр не обязателен, оператор видит всё.
- **Бухгалтер**: разделения нет — отчёты считают всех одинаково. Никаких
  изменений в отчётности.
- **Питающийся**: интерфейс не меняется.

## 12. Безопасность

- Экранирование по RFC 4515 выполняется в модуле.
- Пароли (сервисный и пользовательский) не логируются и не сохраняются.
- `LDAP_TLS=none` допустим только во внутренней сети; в README — предупреждение
  и рекомендация `starttls`/`ldaps`.
- Таймаут на соединение и ответ.
- Сервисная учётка используется только для чтения; записи в каталог не
  выполняются никогда.

## 13. Тестирование

LDAP-клиент подменяется фейковым коннектором — реальный сервер не нужен.

Вход:
- первый вход LDAP-пользователя создаёт `eater` с `auth_source=ldap` и первым
  залом;
- повторный вход не дублирует запись и обновляет ФИО;
- неверный пароль → `401`, запись не создаётся;
- пустой пароль не доходит до клиента;
- локальный оператор входит по паролю, LDAP не вызывается;
- локальный `eater` не перехватывается LDAP (`401`);
- отключённая локально запись → `401`;
- нет активных залов → `503 no_hall_available`;
- каталог недоступен → `503 ldap_unavailable`;
- экранирование: логин `*)(uid=*` не расширяет фильтр.

Синк:
| Случай | Ожидание |
|---|---|
| новый человек в каталоге | создан `eater` с первым залом |
| переименование в каталоге | `full_name` обновлён |
| смена логина | `login` обновлён, если свободен |
| пропал из каталога | `is_active=false`, заявки целы |
| пользователь `local` с тем же логином | не изменён, предупреждение в лог |
| отключённый оператором | не включается обратно |
| пустой фильтр импорта | прогон не выполняется, ошибка в лог |
| каталог недоступен | изменений нет |

Конфигурация: `LDAP_ENABLED=false` — прежнее поведение целиком.

## 14. Выкат и откат

1. Миграция добавляет столбцы; все существующие записи — `local`.
2. Заполнить `LDAP_*` в `.env`, оставить `LDAP_ENABLED=false` — поведение не
   меняется.
3. Включить `LDAP_ENABLED=true`, проверить вход одним тестовым питающимся.
4. Включить `LDAP_SYNC_ENABLED=true` и запустить синк вручную (первый прогон
   создаст весь список — это ожидаемо). Проверить, что в «Студентах» появились
   люди, в «Внешних» — только заведённые вручную.
5. Убедиться, что зал назначен корректно; при необходимости оператор меняет его.

Откат: `LDAP_ENABLED=false` (мгновенно, без пересборки БД). Откат миграции
необязателен и безопасен.

## 15. Известные ограничения

- Совпадение логина локальной учётки и LDAP-пользователя трактуется в пользу
  локальной: такой человек не импортируется и не входит через каталог.
- Автоматически назначается только первый зал; перенос в другой зал — вручную
  оператором.
- Дополнительные атрибуты каталога (почта, телефон, группа) не переносятся:
  для них нет полей в модели.
- Логины приводятся к нижнему регистру; различающиеся только регистром логины
  в каталоге не поддерживаются.
